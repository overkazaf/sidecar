Audio Format Fundamentals

To understand what sidecar does in the audio pipeline, it helps to understand the audio formats it handles. The two primary codecs in the Apple Music ecosystem are ALAC (lossless) and AAC (lossy), each serving different quality tiers.

ALAC — Apple Lossless Audio Codec

ALAC is a lossless audio codec, meaning the decompressed audio is bit-for-bit identical to the original studio master. It achieves roughly 40–60% compression compared to raw PCM, using a combination of two techniques:

Predictive Coding + Entropy Coding — How Lossless Compression Works

Linear Predictive Coding (LPC) — The encoder analyzes each block of samples and fits a linear predictor that estimates each sample from preceding ones. Instead of storing raw sample values, it stores the prediction residuals (the difference between predicted and actual values). For typical music signals, these residuals are much smaller than the raw samples, requiring fewer bits to represent.

Entropy Coding — The residuals are then encoded with a modified Rice code (a type of Golomb code). Rice codes are optimal for geometrically-distributed data, which is exactly what prediction residuals tend to follow. Smaller residuals get shorter codewords, larger ones get longer — achieving compression without any information loss.

The encoder adaptively selects the predictor order (0 to 31) and Rice parameter per block to minimize the encoded size. This is why ALAC compression ratio varies with content: a solo piano piece compresses better than dense EDM because its residuals are more predictable.

Raw PCM:      [1024, 1028, 1031, 1035, 1040, 1038, ...]
Predicted:    [   0, 1024, 1028, 1031, 1035, 1040, ...]
Residual:     [1024,    4,    3,    4,    5,   -2, ...]   ← much smaller values
Rice-coded:   [long,  short, short, short, short, short]  ← fewer bits total

Bit Depth: 16-bit vs 24-bit

Bit depth determines the dynamic range — the ratio between the loudest and quietest sound the format can represent:

Bit DepthDynamic RangeValues per SampleUse Case
16-bit96 dB65,536CD quality — sufficient for most listening
24-bit144 dB16,777,216Hi-Res / studio — exceeds human hearing (120 dB pain threshold)

24-bit audio provides 256× more amplitude resolution than 16-bit. In practice, this extra headroom matters most during production (mixing, mastering) where multiple processing stages accumulate quantization error. For playback, the benefit is the lower noise floor — 24-bit's theoretical -144 dBFS noise is well below any listening environment's ambient noise.

Sample Rate: Nyquist and Human Hearing

The Nyquist-Shannon theorem states that to faithfully represent a signal, the sample rate must be at least twice the highest frequency present. Human hearing tops out around 20 kHz, so:

Sample RateMax FrequencyData Rate (24-bit stereo)Purpose
44.1 kHz22.05 kHz2.12 MbpsCD standard — covers full audible range
48 kHz24 kHz2.30 MbpsVideo/broadcast standard — Apple Music Hi-Res default
96 kHz48 kHz4.61 MbpsUltra-hi-res — used by some studios
192 kHz96 kHz9.22 MbpsArchival — frequencies no human can hear
Why 24-bit / 48 kHz is the sweet spot: It captures the full audible frequency range with generous headroom (24 kHz > 20 kHz), provides 144 dB dynamic range, and keeps file sizes reasonable (~48 MB for a typical 4-minute song). Going to 96 or 192 kHz doubles or quadruples the data with no audible benefit for playback.

Apple Music exclusively uses ALAC for its lossless tier.

AAC — Advanced Audio Coding

AAC is a lossy codec — it achieves much higher compression (roughly 10:1 at 256 kbps) by permanently discarding audio information that the human ear is less likely to perceive. This is fundamentally different from lossless: you cannot recover the original signal from an AAC file.

Psychoacoustic Modeling — How Lossy Compression Decides What to Discard

AAC's encoder uses a psychoacoustic model based on decades of research into human hearing perception:

Simultaneous masking: A loud sound at one frequency makes nearby quieter sounds inaudible. If a cymbal crash at 8 kHz is 80 dB, a quiet detail at 7.5 kHz below 60 dB literally cannot be heard — so AAC doesn't waste bits encoding it.

Temporal masking: A loud transient (like a drum hit) makes sounds immediately before and after it imperceptible. The encoder can reduce precision around transients.

Absolute threshold of hearing: Humans cannot hear sounds below ~4 dB SPL at 1 kHz, and sensitivity drops dramatically above 16 kHz. AAC allocates fewer bits to these regions.

The encoder divides audio into frequency bands using a Modified Discrete Cosine Transform (MDCT), calculates the masking threshold for each band using the psychoacoustic model, and quantizes each band to just above its masking threshold — using enough bits to stay perceptibly transparent, but no more.

Apple chose AAC over MP3 because AAC delivers equivalent quality at ~30% lower bitrate (a 256 kbps AAC file sounds comparable to a 320 kbps MP3), and AAC supports features like proper gapless playback that MP3 lacks.

MP4/M4A Container Format

Audio codecs produce raw compressed data — but to be useful, that data needs a container format that stores metadata, timing information, and enables seeking. Apple Music uses the ISO Base Media File Format (ISO 14496-12), commonly known as MP4. When the container holds only audio, it uses the .m4a extension.

Box (Atom) Structure

An MP4 file is a hierarchy of boxes (also called atoms in Apple's terminology). Each box has a 4-byte size field, a 4-byte type code, and optional contents. Boxes nest arbitrarily deep:

Regular MP4 vs Fragmented MP4 (fMP4)

A regular MP4 has one moov box with a complete sample table (stbl), followed by one large mdat with all audio data. The moov contains every sample's size, offset, and timestamp — enabling instant seeking but requiring the entire file to be written before it's playable.

A fragmented MP4 uses repeating moof + mdat pairs. Each fragment is independently decodable with its own timing info in trun (Track Fragment Run). This is essential for streaming — the receiver can start playback after receiving just the moov + first fragment, without waiting for the entire file.

The multi-description problem: In Apple's fragmented MP4 streams, the stsd box often contains multiple sample description entries (both typed enca for encrypted audio). Fragment 1 references description index 1, while fragments 2–16 reference description index 2. Any processing tool that only handles the first entry will produce a file where only the first fragment plays correctly — the rest decode as silence or noise. This is a common pitfall in working with Apple's HLS-delivered audio.

Sample Description Transformation

When audio is delivered in protected form, the sample description entry is typed enca (encrypted audio) and contains a sinf (protection info) child box. To produce a playable file, two transformations are needed:

  1. Rename enca → alac in the stsd entry's 4-byte type field (for each entry)
  2. Remove the sinf child box and adjust parent sizes accordingly
  3. Neutralize fragment-level protection metadata (senc, saiz, saio boxes in every traf) by overwriting their type with free

The third step is commonly missed — if senc boxes remain, the demuxer still treats the samples as protected even after the stsd rename, resulting in decode failure for all but the first fragment.

Variant Selection Logic

The pipeline's m3u8_select module picks the best variant by:

  1. Filtering for ALAC codec (codecs="alac") when Hi-Res is requested
  2. Among ALAC variants, picking the highest sample rate ≤ the configured maximum (default 192 kHz)
  3. Falling back to AAC-LC 256 kbps if ALAC is unavailable or not requested

In practice, Apple Music typically offers one ALAC variant (24-bit/48 kHz) and one AAC variant (256 kbps) per track.

️ sidecar Architecture Deep Dive

User Namespace Isolation

The core innovation of sidecar is running a chroot-based process pipeline without root privileges, using Linux user namespaces — a kernel feature that creates an isolated view of user/group IDs.

Linux Namespaces Primer

Linux provides 8 types of namespaces, each isolating a different kernel resource:

NamespaceFlagWhat it isolates
UserCLONE_NEWUSERUIDs/GIDs — you can be "root" (uid 0) inside without real root
MountCLONE_NEWNSFilesystem mount table — mounts are private to this namespace
PIDCLONE_NEWPIDProcess IDs — child sees itself as PID 1
NetworkCLONE_NEWNETNetwork devices, ports, routing tables
IPCCLONE_NEWIPCSystem V IPC, POSIX message queues
UTSCLONE_NEWUTSHostname and domain name
CgroupCLONE_NEWCGROUPCgroup root directory
TimeCLONE_NEWTIMEBoot and monotonic clocks

sidecar uses only User + Mount — the minimum needed for rootless chroot with bind mounts. This is far lighter than Docker (which uses 5+ namespaces + cgroups + overlay filesystem).

Step-by-Step Namespace Setup

// 1. Save real UID/GID BEFORE unshare (critical — getuid() returns 65534 after)
uid_t real_uid = getuid();  // e.g., 1000
gid_t real_gid = getgid();  // e.g., 1000

// 2. Create new user + mount namespace
unshare(CLONE_NEWUSER | CLONE_NEWNS);

// 3. Map real user to root INSIDE the namespace
write("/proc/self/setgroups", "deny\n");        // required before gid_map
write("/proc/self/uid_map", "0 1000 1\n");      // ns-uid-0 = host-uid-1000
write("/proc/self/gid_map", "0 1000 1\n");      // ns-gid-0 = host-gid-1000

// 4. Now we're "root" inside — mount and chroot work
mount("/dev",  "rootfs/dev",  NULL, MS_BIND|MS_REC, NULL);
mount("/proc", "rootfs/proc", NULL, MS_BIND|MS_REC, NULL);
mount("/sys",  "rootfs/sys",  NULL, MS_BIND|MS_REC, NULL);

// 5. Enter the rootfs
chroot("rootfs");
chdir("/");
execv("/system/bin/main", child_argv);
Common pitfall: Calling getuid() after unshare(CLONE_NEWUSER) but before writing uid_map returns 65534 (the "nobody" overflow UID). The uid/gid map must use the real UID captured before the unshare call. This bug caused early sidecar versions to fail with "Operation not permitted" when writing uid_map.

Process Lifecycle

PTY Allocation: Why openpty() Matters

When a process's stdout is a pipe (the default for subprocess communication), the C library defaults to fully buffered output — writes accumulate in a 4 KB internal buffer and only flush when full or on fflush(). This means a child process's progress messages may not appear for minutes.

sidecar allocates a pseudo-terminal (PTY) via openpty(). When stdout is a TTY, libc switches to line-buffered mode — each \n triggers a flush. This makes child output visible in real time, critical for observability during login and initialization.

Port Readiness Detection

After the child starts inside the chroot, it takes several seconds to initialize (loading libraries, establishing auth state). sidecar needs to know when the service is actually ready to accept connections.

The approach: non-blocking TCP connect probes on a 200ms tick, interleaved with PTY drain. The interleaving is critical — the child process writes >4 KB of output during startup (library loading messages). If sidecar blocked on TCP probes without draining the PTY, the PTY buffer would fill, the child's write() would block, and startup would deadlock.

while (!all_ports_ready && !timed_out) {
    // 1. Drain any pending PTY output (non-blocking read)
    drain_pty(master_fd);

    // 2. Probe each port with non-blocking connect
    for (port : wait_ports) {
        fd = socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK, 0);
        connect(fd, port);  // returns immediately (EINPROGRESS)
        poll(fd, POLLOUT, 50ms);  // short timeout
        if (connected) mark_ready(port);
        close(fd);
    }

    usleep(200_000);  // 200ms tick
}

⚡ Optimization Principles

M4A Writer: In-Place Patching Strategy

After samples are processed, they need to be written back into a valid ALAC M4A file. The naive approach would be to construct a new file from scratch — but this requires understanding every box type in the original container, which is fragile and lossy.

Instead, sidecar's pipeline uses in-place byte patching: the original fragmented MP4 is modified in memory, with processed samples overwriting their original counterparts at the exact same byte offsets. Since processing preserves sample sizes (sample_in.length == sample_out.length), no box sizes need to change for the mdat regions.

The structural changes needed are minimal:

1. stsd Entry Rename

Overwrite the 4-byte type field of every enca entry with alac. Remove the sinf child box and adjust all ancestor box sizes. Must handle multiple entries (the common failure mode is patching only the first).

2. sinf Removal

The sinf box inside each enca entry describes the protection scheme. Removing it requires shrinking the entry and every parent box (stsd → stbl → minf → mdia → trak → moov) by the sinf's size.

3. Fragment Metadata Neutralization

Each traf contains senc (IVs), saiz (aux sizes), saio (aux offsets). These are overwritten with free boxes — same size, preserving all byte offsets, but invisible to demuxers.

Why not just remux with ffmpeg? Running ffmpeg -c copy -movflags +faststart on a fragmented ALAC file often produces a truncated result. ffmpeg's copy-mode remuxer reads duration from the moov header, which in fragmented MP4 only describes the first segment (~15s). The remaining fragments' moof/mdat pairs are silently dropped. In-place patching preserves all fragments.

Pipeline Concurrency

A single processing instance on TCP 47010 handles one connection at a time (fork-per-connection, serial within each fork). For album downloads (10–20 tracks), this is the throughput bottleneck.

Multi-Instance Architecture

aria server (Flask, threaded)
    │
    ├── DecryptPool (round-robin, per-instance mutex)
    │   ├── sidecar :47010 / :47020  (instance 0)
    │   ├── sidecar :47011 / :47021  (instance 1)
    │   ├── sidecar :47012 / :47022  (instance 2)
    │   └── sidecar :47013 / :47023  (instance 3)
    │
    └── Per request: pick least-busy → lock → process → unlock

Each sidecar instance is an independent process with its own TCP ports. The DecryptPool dispatches tracks using round-robin selection with per-instance mutex locks — ensuring only one track uses each instance at a time.

Why persistent connections fail — and the per-track connection solution

Initially, the pipeline reused TCP connections across tracks (a PersistentDecryptSession). This failed because the processing service maintains internal session state per-connection — when a second track's key context arrived on the same connection, the state machine could enter an invalid state, causing the service to crash or hang.

The fix is straightforward: open a new TCP connection for each track. The connection setup overhead (~1ms on loopback) is negligible compared to the processing time per track (~4s for a typical 48MB ALAC file). This trades a tiny latency increase for complete stability — the pipeline now processes 19-track albums with zero failures.

Memory & I/O Optimization

Pipelined Processing Protocol

The TCP protocol uses a pipelined writer/reader design with a semaphore gate to balance throughput and memory:

Writer thread                          Processing service
    │                                       │
    ├── send(key_context_header) ──────────►│
    ├── send(sample_1_len + data) ─────────►│ process sample 1
    ├── send(sample_2_len + data) ─────────►│ process sample 2
    │   ... (up to 64 in-flight)            │
    │                                       │
Reader thread                               │
    ├── recv(processed_sample_1) ◄──────────│
    │   gate.release()  ← allows writer     │
    ├── recv(processed_sample_2) ◄──────────│
    │   gate.release()                      │
    │   ...                                 │

The semaphore gate (capacity 64) ensures at most 64 samples are in-flight — preventing unbounded memory growth while keeping the TCP pipe full. With 256KB socket buffers and ~18KB average sample size, this achieves ~12 MB/s throughput on loopback.

Quick Start

# Build
make
# or: cc -O2 -Wall -Wextra -o sidecar sidecar.c -lutil

# Verify user namespace support
cat /proc/sys/kernel/unprivileged_userns_clone   # should be 1

# Run (no root needed)
./sidecar --rootfs ./rootfs --bin /system/bin/main \
  --wait-ports 47010,47020 --verbose \
  -- -M 47020 -D 47010 -F

# Multi-instance (4 parallel)
for i in 0 1 2 3; do
  ./sidecar --rootfs ./rootfs --bin /system/bin/main \
    --wait-ports $((47010+i)),$((47020+i)) \
    -- -M $((47020+i)) -D $((47010+i)) -F &
done

# Graceful restart (refresh auth without process exit)
kill -USR1 $(pgrep -f sidecar)
