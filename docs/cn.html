音频格式基础

要理解 sidecar 在音频流水线中的作用，需要先了解它处理的音频格式。Apple Music 生态系统中的两种主要编解码器是 ALAC（无损）和 AAC（有损），分别服务于不同的音质层级。

ALAC — Apple 无损音频编解码器

ALAC 是一种无损音频编解码器，解压后的音频与原始录音室母带完全一致（逐比特相同）。相较于原始 PCM，它实现了约 40-60% 的压缩率，使用两种技术的组合：

预测编码 + 熵编码 — 无损压缩的工作原理

线性预测编码（LPC） — 编码器分析每个采样块，拟合一个线性预测器来根据前序采样估计当前采样。它不存储原始采样值，而是存储预测残差（预测值与实际值之间的差异）。对于典型的音乐信号，这些残差远小于原始采样值，所需的比特数更少。

熵编码 — 残差随后使用改进的 Rice 编码（一种 Golomb 编码）进行编码。Rice 编码对几何分布数据是最优的，而预测残差恰好倾向于遵循这种分布。较小的残差获得较短的码字，较大的获得较长的——在不丢失任何信息的情况下实现压缩。

原始 PCM:     [1024, 1028, 1031, 1035, 1040, 1038, ...]
预测值:       [   0, 1024, 1028, 1031, 1035, 1040, ...]
残差:         [1024,    4,    3,    4,    5,   -2, ...]   <-- 值小得多
Rice 编码:    [长,   短,   短,   短,   短,   短]          <-- 总比特更少

位深度：16 位 vs 24 位

位深度决定了动态范围——格式能表示的最大音量与最小音量之间的比值：

位深度动态范围每采样值数用途
16 位96 dB65,536CD 音质——满足大多数聆听场景
24 位144 dB16,777,216Hi-Res / 录音室——超过人耳极限（120 dB 痛阈）

24 位音频提供比 16 位多 256 倍的振幅分辨率。实际上，这额外的余量在制作阶段（混音、母带处理）最为重要，因为多次处理会累积量化误差。对于回放，其优势在于更低的噪声本底——24 位的理论 -144 dBFS 噪声远低于任何聆听环境的背景噪声。

采样率：奈奎斯特与人类听觉

奈奎斯特-香农采样定理指出，要忠实地表示一个信号，采样率必须至少是信号中最高频率的两倍。人类听觉上限约为 20 kHz，因此：

采样率最高频率数据率（24 位立体声）用途
44.1 kHz22.05 kHz2.12 MbpsCD 标准——覆盖完整可听频率范围
48 kHz24 kHz2.30 Mbps视频/广播标准——Apple Music Hi-Res 默认值
96 kHz48 kHz4.61 Mbps超高解析度——部分录音室使用
192 kHz96 kHz9.22 Mbps存档——包含人耳无法听到的频率
为什么 24 位 / 48 kHz 是最佳平衡点：它覆盖了完整的可听频率范围并留有充裕余量（24 kHz > 20 kHz），提供 144 dB 动态范围，同时文件大小合理（一首约 4 分钟的歌曲大约 48 MB）。提升到 96 或 192 kHz 会使数据量翻倍或翻四倍，但回放时没有可感知的音质提升。

AAC — 高级音频编码

AAC 是有损编解码器——通过永久丢弃人耳不太可能感知的音频信息，实现更高的压缩比（256 kbps 时约 10:1）。这与无损有本质区别：你无法从 AAC 文件恢复原始信号。

心理声学模型 — 有损压缩如何决定丢弃什么

同时掩蔽：一个频率上的响亮声音会使附近较安静的声音变得不可听。如果 8 kHz 处有 80 dB 的钹声，7.5 kHz 处低于 60 dB 的细节字面上无法被听到——因此 AAC 不浪费比特编码它。

时间掩蔽：一个响亮的瞬态（如鼓击）会使其前后的声音变得不可感知。编码器可以降低瞬态周围的精度。

绝对听阈：人类在 1 kHz 处无法听到低于约 4 dB SPL 的声音，且灵敏度在 16 kHz 以上急剧下降。AAC 为这些区域分配更少的比特。

AAC 变体

规格码率范围用途
AAC-LC（低复杂度）128-320 kbpsApple Music 标准层级（256 kbps）。高码率下最佳质量比。
HE-AAC（v1）48-96 kbps低带宽流媒体。使用频谱带复制（SBR）重建高频。

Apple Music 使用 AAC-LC 256 kbps——在盲听测试中被认为对大多数听众"透明"。Apple 选择 AAC 而非 MP3，因为 AAC 在约低 30% 的码率下实现等效音质（256 kbps AAC 听起来与 320 kbps MP3 相当），且 AAC 支持正确的无缝播放等 MP3 缺乏的特性。

MP4/M4A 容器格式

音频编解码器产生原始压缩数据——但要有用，这些数据需要一种存储元数据、时序信息并支持搜索定位的容器格式。Apple Music 使用 ISO 基础媒体文件格式（ISO 14496-12），通常称为 MP4。当容器仅包含音频时，使用 .m4a 扩展名。

Box（Atom）结构

MP4 文件是 Box（在 Apple 术语中也称为 Atom）的层级结构。每个 Box 有 4 字节大小字段、4 字节类型码和可选内容。Box 可以任意深度嵌套：

普通 MP4 vs 分片 MP4（fMP4）

普通 MP4 有一个包含完整采样表（stbl）的 moov Box，后跟一个包含所有音频数据的大 mdat。moov 包含每个采样的大小、偏移量和时间戳——支持即时定位，但要求整个文件写完才能播放。

分片 MP4 使用重复的 moof + mdat 对。每个分片通过 trun（轨道分片运行）中的独立时序信息可独立解码。这对流媒体至关重要——接收端只需收到 moov + 第一个分片即可开始播放，无需等待整个文件。

多描述问题：在 Apple 的分片 MP4 流中，stsd Box 通常包含多个采样描述条目（均为 enca 类型的加密音频）。分片 1 引用描述索引 1，而分片 2-16 引用描述索引 2。任何只处理第一个条目的工具都会产生一个只有第一个分片能正确播放的文件——其余解码为静音或噪声。

采样描述转换

当音频以受保护形式交付时，采样描述条目类型为 enca（加密音频），包含 sinf（保护信息）子 Box。要产生可播放文件，需要三个转换：

  1. 重命名 stsd 条目中每个 enca 的 4 字节类型字段为 alac
  2. 移除 sinf 子 Box 并相应调整父级大小
  3. 中和每个 traf 中的分片级保护元数据（senc、saiz、saio Box），将其类型覆写为 free

第三步通常被遗漏——如果 senc Box 保留，解复用器仍将采样视为受保护的，即使 stsd 已重命名，也会导致除第一个分片外的所有分片解码失败。

sidecar 架构深入解析

用户命名空间隔离

sidecar 的核心创新是无需 root 权限运行基于 chroot 的进程流水线，使用 Linux 用户命名空间——一种创建 UID/GID 隔离视图的内核特性。

Linux 命名空间入门
命名空间标志隔离内容
UserCLONE_NEWUSERUID/GID——命名空间内可以成为"root"而不拥有真实 root
MountCLONE_NEWNS文件系统挂载表——挂载对该命名空间私有
PIDCLONE_NEWPID进程 ID——子进程视自己为 PID 1
NetworkCLONE_NEWNET网络设备、端口、路由表

sidecar 仅使用 User + Mount——无需 root 的 chroot + bind mount 所需的最小集。这比 Docker（使用 5+ 种命名空间 + cgroups + overlay 文件系统）轻量得多。

分步命名空间设置

// 1. 在 unshare 之前保存真实 UID/GID（关键——unshare 后 getuid() 返回 65534）
uid_t real_uid = getuid();  // 例如 1000
gid_t real_gid = getgid();  // 例如 1000

// 2. 创建新的 user + mount 命名空间
unshare(CLONE_NEWUSER | CLONE_NEWNS);

// 3. 将真实用户映射为命名空间内的 root
write("/proc/self/setgroups", "deny\n");        // gid_map 之前必须
write("/proc/self/uid_map", "0 1000 1\n");      // ns-uid-0 = 宿主-uid-1000
write("/proc/self/gid_map", "0 1000 1\n");      // ns-gid-0 = 宿主-gid-1000

// 4. 现在我们在命名空间内是"root"——mount 和 chroot 可以工作
mount("/dev",  "rootfs/dev",  NULL, MS_BIND|MS_REC, NULL);
mount("/proc", "rootfs/proc", NULL, MS_BIND|MS_REC, NULL);

// 5. 进入 rootfs
chroot("rootfs");
chdir("/");
execv("/system/bin/main", child_argv);
常见陷阱：在 unshare(CLONE_NEWUSER) 之后但写入 uid_map 之前调用 getuid() 会返回 65534（"nobody" 溢出 UID）。uid/gid 映射必须使用在 unshare 调用之前捕获的真实 UID。此 bug 导致早期 sidecar 版本在写入 uid_map 时报"Operation not permitted"。

进程生命周期

PTY 分配：为什么 openpty() 重要

当进程的 stdout 是管道时（子进程通信的默认方式），C 库默认使用全缓冲输出——写入累积在 4 KB 内部缓冲区中，只在缓冲区满或调用 fflush() 时才刷新。这意味着子进程的进度消息可能数分钟不显示。

sidecar 通过 openpty() 分配伪终端（PTY）。当 stdout 是 TTY 时，libc 切换到行缓冲模式——每个 \n 触发一次刷新。这使子进程输出实时可见，对登录和初始化过程的可观测性至关重要。

信号转发链

操作者发送 SIGTERM
    |
    v
sidecar（父进程）捕获信号
    |
    +-- 转发 SIGTERM 到子进程组
    +-- 启动优雅超时计时器（--grace-secs，默认 10s）
    +-- 继续排空 PTY 输出
    +-- [子进程在优雅期内退出？]
    |   +-- 是 -> 收集退出状态，以相同代码退出
    |   +-- 否 -> 发送 SIGKILL，收集，退出
    |
SIGUSR1（优雅重启）:
    +-- 相同的 TERM -> 等待 -> KILL 序列
    +-- 子进程退出后 -> 使用相同 argv 重新 fork
        （sidecar PID 不变——服务不中断）

端口就绪检测

方法：以 200ms 间隔进行非阻塞 TCP 连接探测，与 PTY 排空交替执行。交替执行至关重要——子进程在启动期间输出超过 4 KB 的内容。如果 sidecar 在 TCP 探测上阻塞而不排空 PTY，PTY 缓冲区会满，子进程的 write() 会阻塞，启动会死锁。

优化原理

M4A 写入器：原地修补策略

采样处理后需要写回有效的 ALAC M4A 文件。朴素方法是从头构建新文件——但这要求理解原始容器中的每种 Box 类型，既脆弱又有信息损失。

sidecar 的流水线使用原地字节修补：原始分片 MP4 在内存中被修改，处理后的采样在完全相同的字节偏移处覆写原始对应物。由于处理保持采样大小不变（sample_in.length == sample_out.length），mdat 区域的 Box 大小不需要改变。

1. stsd 条目重命名

覆写每个 enca 条目的 4 字节类型字段为 alac。移除 sinf 子 Box 并调整所有祖先 Box 大小。必须处理多个条目。

2. sinf 移除

每个 enca 条目内的 sinf Box 描述保护方案。移除它需要缩小该条目及每个父级 Box（stsd - stbl - minf - mdia - trak - moov）。

3. 分片元数据中和

每个 traf 包含 senc（IV）、saiz（辅助大小）、saio（辅助偏移）。它们被覆写为 free Box——相同大小，保留所有字节偏移，但对解复用器不可见。

为什么不用 ffmpeg 重新封装？对分片 ALAC 文件运行 ffmpeg -c copy -movflags +faststart 通常产生截断结果。ffmpeg 的 copy 模式从 moov 头读取时长，而分片 MP4 中 moov 仅描述第一个段（约 15 秒）。其余分片的 moof/mdat 对被静默丢弃。原地修补保留所有分片。

流水线并发

单个处理实例在 TCP 47010 上一次处理一个连接。对于专辑下载（10-20 首），这是吞吐量瓶颈。

为什么持久连接会失败——以及每轨道连接的解决方案

最初，流水线跨轨道复用 TCP 连接（PersistentDecryptSession）。这失败了，因为处理服务在每个连接上维护内部会话状态——当第二首歌的 key context 到达同一连接时，状态机进入无效状态，导致服务崩溃或挂起。

修复很直接：为每首歌打开新的 TCP 连接。连接建立开销（回环上约 1ms）相对于每首歌的处理时间（典型 48MB ALAC 文件约 4s）可以忽略。这以微小的延迟增加换取了完全的稳定性——流水线现在处理 19 首专辑时零失败。

快速开始

# 编译
make
# 或: cc -O2 -Wall -Wextra -o sidecar sidecar.c -lutil

# 验证用户命名空间支持
cat /proc/sys/kernel/unprivileged_userns_clone   # 应为 1

# 运行（无需 root）
./sidecar --rootfs ./rootfs --bin /system/bin/main \
  --wait-ports 47010,47020 --verbose \
  -- -M 47020 -D 47010 -F

# 多实例（4 个并行）
for i in 0 1 2 3; do
  ./sidecar --rootfs ./rootfs --bin /system/bin/main \
    --wait-ports $((47010+i)),$((47020+i)) \
    -- -M $((47020+i)) -D $((47010+i)) -F &
done

# 优雅重启
kill -USR1 $(pgrep -f sidecar)
