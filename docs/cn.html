⚙ 架构

sidecar 创建一个隔离的 Linux 用户命名空间，将宿主机内核接口 bind-mount 到 Android rootfs 中， 然后在 chroot 内 exec FairPlay 解密二进制。子进程通过两个原始 TCP 端口提供 流式解密和 HLS URL 解析服务。

sidecar (PID 1, 用户空间) │ ├─ unshare(CLONE_NEWUSER | CLONE_NEWNS) │ ├─ 写入 /proc/self/uid_map → 0 <真实uid> 1 │ └─ 写入 /proc/self/gid_map → 0 <真实gid> 1 │ ├─ bind-mount /dev, /proc, /sys → rootfs/ ├─ 同步 /etc/{resolv.conf, hosts} → rootfs/etc/ │ ├─ chroot("./rootfs") │ └─ exec /system/bin/main (FairPlay 解密守护进程) │ ├─ TCP :47010 — 解密（逐 sample 流密码） │ └─ TCP :47020 — m3u8（HLS 主播放列表解析） │ └─ 监管循环 ├─ PTY 缓冲区排空 (行缓冲子进程输出) ├─ 端口就绪门控 (--wait-ports) ├─ SIGUSR1 → 优雅重启 (重新 fork, PID 不变) └─ SIGTERM → 优雅关闭 (TERM → 等待 → KILL)

⚡ 为什么选择 sidecar

社区已经构建了出色的 Apple Music ALAC 解密工具。sidecar 在此基础上， 专注解决实际生产部署中遇到的痛点：

无需 Root 权限

通过用户命名空间隔离（unshare），将用户 UID 映射为命名空间内的 root。 无需 sudo，无需特权能力，无需 Docker 守护进程。

完整可观测性

PTY 转发的子进程输出（行缓冲，实时可见）。--json-events 提供机器可解析的状态事件。 --verbose 提供人类可读的进度信息。

端口就绪门控

--wait-ports 47010,47020 会阻塞直到解密守护进程真正开始监听。 无需盲等或轮询。

优雅生命周期管理

SIGUSR1 在不重启 sidecar 本身的情况下重新 fork 子进程。 SIGTERM 发起可配置超时的优雅关闭。

DNS 引导

自动将 resolv.conf、hosts 和 nsswitch.conf 同步到 chroot 中。避免静默的 DNS 解析失败。

单 C 文件

923 行代码，除 libc + libutil 外零依赖。make 即可编译。 一个下午即可审计完整个代码库。

🚀 快速开始

编译

# 克隆并编译
git clone https://github.com/overkazaf/sidecar.git
cd sidecar
make          # → ./sidecar (39 KB)

运行（从文件读取认证，无需登录）

./sidecar --userns --rootfs ./rootfs --bin /system/bin/main \
  --wait-ports 47010,47020 --verbose \
  -- -M 47020 -D 47010 -F

登录模式（首次认证）

./sidecar --userns --rootfs ./rootfs --bin /system/bin/main \
  --wait-ports 47010,47020 --verbose \
  -- -M 47020 -D 47010 --login=user@host:pass

多实例（4 个并行解密 worker）

for i in 0 1 2 3; do
  ./sidecar --userns --rootfs ./rootfs --bin /system/bin/main \
    --wait-ports $((47010+i)),$((47020+i)) \
    -- -M $((47020+i)) -D $((47010+i)) -F &
done

优雅重启（刷新认证无需重启 sidecar）

kill -USR1 $(pgrep -f sidecar)

🛠 命令行参数

参数默认值说明
--rootfs PATH./rootfsAndroid rootfs 目录
--bin PATH/system/bin/mainchroot 内执行的二进制文件
--userns开启使用用户命名空间（无需 root）。--no-userns 使用真实 chroot
--wait-ports P,P—阻塞直到指定 TCP 端口响应
--wait-timeout N120等待端口就绪的超时秒数
--grace-secs N10SIGTERM 与 SIGKILL 之间的等待秒数
--verbose关闭向 stderr 输出设置步骤
--json-events关闭在 stderr 输出机器可读的 JSON 状态
--pid-file PATH—写入子进程 PID，用于 systemd/k8s 探测
--ready-fd N—端口就绪时向 fd N 写入 \1\n
--—之后的所有参数原样传递给子进程

🔌 通信协议

FairPlay 解密二进制暴露两个原始 TCP 端口。均为本地无认证、长度前缀的二进制帧格式。

端口 47020 — m3u8（获取流地址）

将 Apple Music adamId 解析为 enhanced-HLS 主播放列表 URL。

客户端 → 服务端:  0a 31 34 34 30 38 34 31 32 36 33
                  └─┘ └────── '1440841263' ──────┘
                  长度

服务端 → 客户端:  "https://aod-ssl.itunes.apple.com/...master.m3u8\n"

端口 47010 — 解密（逐 sample）

全双工流水线流密码通道。每个连接支持多个 key context。

# Key context 头（每个 key 一次）:
len(adamId) adamId len(keyUri) keyUri

# 每个 sample（重复）:
LE-uint32 sample_len 密文[sample_len]  →  明文[sample_len]

# 结束 context:
00 00 00 00

🔗 与 aria 集成

aria 是编排完整 ALAC 流水线的 HTTP API 服务： Apple 目录查询 → HLS 下载 → 通过 sidecar 进行 FairPlay 解密 → m4a 输出。 

# aria_sidecar.py 管理 N 个 sidecar 实例
python3 aria_sidecar.py -F --instances 4

# aria 服务器在实例间轮询分发解密请求
ARIA_INSTANCES=4 python3 server.py --port 8899

# 下载 Hi-Res ALAC
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8899/download/1440841263?fmt=alac" \
  -o song.m4a
